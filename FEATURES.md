KRNL vs. a minimal usable Linux distro — gap analysis
Based on a full read of kernel/src, the mlibc syscall shim, and the userspace bootstrap manifest. Current state in one line: boots via UEFI/Limine → mounts ext2 (AHCI) or a ramdisk → execs init → init forks+execs bash (respawning it if it ever exits or crashes, and reaping any orphans in between) with full GNU coreutils, over a serial console. That's a real foundation — closer to "minimal distro" than most hobby kernels get. The gaps below are sorted by how much they block generic, everyday usability (not by implementation difficulty).

Tier 1 — Blocks basic interactive/day-to-day use
[RESOLVED] TTY line discipline (canonical mode, echo, Ctrl‑C/Ctrl‑Z signal generation) — tty.c now implements real canonical-mode line buffering/editing (VERASE/VKILL/VEOF), ECHO with OPOST/ONLCR, and ISIG-driven SIGINT/SIGQUIT/SIGTSTP delivered to the foreground process group. Real process groups exist (process_t.pgid/sid, setpgid/getpgid/setsid/getsid syscalls, mlibc's stubs replaced), and a kernel-wide bug where signals were never delivered to threads blocked in a kernel-context wait (waitpid/nanosleep/tty read/pipe/futex) was found and fixed. Ctrl‑C/Ctrl‑Z/fg/bg/jobs all confirmed working against both `cat` and `sleep`. Waitpid unblocking a parent never actually depended on a real SIGCHLD *signal* reaching it — it's a plain `sleep()`/`wakeup()` broadcast keyed off pid, independent of signal delivery — and that's good, because actually delivering a real SIGCHLD signal to a process's parent (attempted, then reverted, during the process-reaping work below) turned out to be unsafe: `process_t.parent` was a raw pointer that process_fork() never even set (always NULL, a real pre-existing bug — see below), so SIGCHLD-to-parent had silently never fired for any forked process in this kernel's history. Making it actually fire exposed a real, previously-dormant bug where bash's own `sigchld_handler` reproducibly re-runs the just-stopped foreground command from history the first time it's ever invoked live. Deliberately left un-fixed and un-delivered (see process.c comments) — a real bash/mlibc bug, same flavor as the pselect/utf8_charcode saga, worth a dedicated follow-up. Known residual gaps: bash's own readline occasionally crashes on signal delivery (pre-existing bug in bundled bash/mlibc, out of scope — see memory), and `fg` resuming a stopped job doesn't always cleanly restore interactive input.
[RESOLVED] No /dev device-node infrastructure — /dev/null, /dev/zero, /dev/random, /dev/urandom now exist (memdev.c) alongside /dev/tty0.
No text-processing toolset — sys-apps.yml only builds bash + coreutils 8.32. There's no grep, sed, awk, findutils, less/more, or a text editor (vi/nano). Coreutils alone (ls/cp/mv/cat/...) isn't enough to call a system "usable" for real work.
[PARTIALLY RESOLVED, see above] — grep/sed/gawk/findutils added to sys-apps.yml and confirmed working (including `find`'s real directory traversal, which needed new fchdir/openat/fstatat(fd_path) kernel support — see below). `less`/`more`/an editor are still missing (less needs a termcap/curses library that isn't cross-compiled for this target — a separate, larger porting effort). [RESOLVED] `xargs`'s crash and the `find | xargs` hang: the earlier "EIO on the child's own I/O" theory was a misdiagnosis — xargs actually crashed immediately on *every* invocation via `opendir("/proc/self/fd")` (no real `/proc/self/fd` exists), which `vfs_find_mount`'s "/" catch-all + `vfs_open_dir` skipping existence checks let spuriously succeed, only to hard-abort in mlibc's `readdir()` on the first `-ENOENT`. Fixed by having `vfs_open_dir` (`kernel/src/vfs/vfs.c`) validate the path via `vfs_fstat` (which already covers real directories and x1fs/mount-overlay implicit directories) before succeeding. The pipeline hang was a separate bug: `process_exit()` never closed a dying process's fds — that was deferred to `process_destroy()`, which only runs once the parent reaps the zombie — so a pipe's dead reader (e.g. crashed xargs) kept its read end "open" until reaped, and a writer (`find`) filling the 64KB pipe buffer first would block forever. Fixed by moving fd/pipe cleanup into `process_exit()` itself (`kernel/src/process/process.c`). Confirmed via headless boot: `echo x | xargs echo` and `find /usr/bin | xargs echo | wc -l` both complete with exit 0, no crash, no hang; `/proc/self/fd` now correctly ENOENTs while `/proc`, `/dev`, `/`, and real directories still open fine.
Keyboard/console not wired for local (non-serial) use — the PS/2 driver (ps2/keyboard.c) and framebuffer text renderer (framebuffer.c) both work standalone but are never connected to the TTY/stdin path; only a serial line is usable as a terminal today.
[RESOLVED] Permissions are entirely unenforced — real chmod/fchmod/fchmodat and chown/fchown/fchownat now exist end-to-end: new `chmod`/`chown` ops on `vfs_fs_t`, backed by real on-disk inode mode/uid/gid updates in ext2 and by new mode/uid/gid fields on x1fs's RAM-overlay dyn entries (baked/static x1fs entries stay immutable, same rule as their existing read-only-write restriction). `open()`'s long-ignored `mode` argument (previously hardcoded to 0644 for every `O_CREAT`) is now actually threaded through. `syscall_fchownat` was a hard `-ENOSYS` stub and `chmod`/`chown`/`fchmodat` had no mlibc krnl sysdep glue at all (dead syscalls, unreachable from userspace) — both fixed, plus a new `fchmodat` syscall (kernel + mlibc). Enforcement itself lives in syscall.c: a shared `check_access()` helper (root bypass; else owner/group/other bits against the caller's uid/gid) is wired into `resolve_at()`'s existing path-walk for X_OK directory-traversal checks on every ancestor component, plus R_OK/W_OK on open(), W_OK on the containing directory for mkdir/unlink/rmdir/rename/symlink, and X_OK on the target for execve. chmod requires root or ownership; chown is root-only (this kernel doesn't track supplementary groups, so the full POSIX "owner may chgrp to a group they belong to" rule can't be checked — simplified to root-only, a safe subset). New files/dirs/symlinks created by a non-root process are chowned to that process's uid/gid immediately after creation (ext2/x1fs's own create/mkdir/symlink ops take no uid/gid of their own). Also added `setuid()`/`setgid()` (the latter's kernel handler existed but, like fchownat, had no mlibc glue either) — both unrestricted (any process can assume any uid/gid), since process_t has no distinct real/effective/saved-id triple yet to enforce POSIX's non-root transition rule against; good enough to drop privilege for testing, revisit once real multi-user/login lands. Confirmed with a disposable test program exercising the whole stack (create/chmod/chown/stat round-trip, root bypass of a 0000 file, `setuid` privilege drop, owner-vs-non-owner open/chmod/chown, and mkdir denied under a 0555 directory): 18/18 checks passed on a fresh headless boot on **both** ext2 and x1fs.
[RESOLVED] No process reaping / real init — init.c now forks bash instead of exec-replacing itself, and loops on `waitpid(-1, &status, 0)` forever: any pid it reaps that isn't the current shell's pid is just a reparented orphan being cleaned up, and if the shell itself exits or crashes it's immediately respawned. This needed a real kernel-side fix, not just a userspace rewrite: `process_exit()` previously only ever notified `process->parent` (a cached raw pointer) and never touched a dying process's own children at all, so any process that exited before its parent left its children's `ppid` pointing at a pid nobody would ever match again in `scheduler_waitpid`'s comparators — permanently unreapable, not just "eventually reaped." Fixed with a new `scheduler_reparent_children(old_ppid, new_ppid)` (scheduler.c) called from `process_exit()`, which walks the scheduler queue and rewrites `ppid` for every direct child of the exiting process to init's pid (tracked once, in `process_init()`, since this kernel doesn't reserve pid 1 — init's actual pid is whatever `scheduler_get_free_pid_locked()` hands out first, currently 101). Along the way, found and fixed a real, independent, always-on bug: `process_fork()` never set `child->parent` (always NULL for every forked process, ever), which meant `getppid()` — which read `proc->parent->pid` — returned `-1` for every process in the system except init itself. Fixed by having `getppid()` return the authoritative `proc->ppid` integer directly instead of dereferencing a pointer at all, and by resolving "the parent" via `scheduler_get_process_by_pid(ppid)` (a fresh, safe lookup) instead of a cached pointer anywhere it's still needed — which also incidentally closed a latent use-after-free (a reparented/reaped parent's freed `process_t` being dereferenced by a child that outlived it). The now-fully-dead `process_t.parent` field was removed outright. See the TTY entry above for why real SIGCHLD-to-parent delivery specifically was attempted, found to regress bash, and deliberately reverted. Confirmed on a fresh headless boot: `$PPID` correctly reports init's pid (101) instead of the old always-broken value; `( sleep 3 & )` (a subshell backgrounding then immediately exiting, orphaning the child) is reparented to init and reaped a few seconds later — traced live via temporary instrumentation, then removed; and `exit`-ing the shell (or it crashing) is immediately followed by a brand-new bash prompt on the same tty with a fresh pid, with no user action needed. `/etc/fstab` mounting was **not** implemented — there's still no `mount()`/`umount()` syscall at all (root + `/dev/tty0` are hardcoded in `boot.c`), so "mounting fstab entries" isn't achievable yet without that separate, larger Tier-2 syscall first; scoped out of this pass.
Tier 2 — Missing core OS functionality expected by generic userspace software
[RESOLVED] select/poll are fake (fd readiness always reports ready) — pselect now does real fd-readiness checking instead of reporting every requested fd ready unconditionally. Added a `poll` op to vfs_fs_t (device_major/minor/path/for_write -> ready?), NULL meaning "always ready" (correct for regular files/memdev, whose I/O is synchronous and never blocks); tty.c implements it against the same cooked-buffer/EOF state tty_read already blocks on, and pipes are checked directly against their buffer count/reader/writer state (mirroring pipe_read/pipe_write's own blocking conditions). There's still no true event-driven multi-fd wait (sleep()/wakeup() only support one wait channel per call), so an unready set is polled at the scheduler's HPET tick granularity (~77ms) until something is ready or the timeout elapses — correct, if not maximally efficient; still the right fix for correctness-sensitive callers (anything that only reads/writes an fd after select/pselect reports it ready). Confirmed via a fresh kernel build + full headless serial-console boot to a bash prompt with no regressions in the boot path.
[RESOLVED] No named pipes / FIFOs at the kernel level — real `mkfifo`/`mkfifoat` now exist (new `SYS_MKFIFOAT` syscall, `S_IFIFO`/`S_ISFIFO` in vfs.h, ext2 and x1fs backends) and open() on a FIFO path rendezvous-and-blocks correctly (O_RDONLY waits for a writer, O_WRONLY waits for a reader or -ENXIO under O_NONBLOCK, O_RDWR never blocks), reusing the existing anonymous-pipe machinery in pipe.c. Fixed two bugs found along the way: `stat()`/`statx()` are implemented via a real open()+fstat()+close() internally, which used to hang forever on a FIFO path until exempted via O_PATH; and `pipe_dup`/`pipe_close` mishandled O_RDWR (only possible via FIFOs), leaking a refcount. Verified solid with 5 repeated background/write/read cycles on ext2 (the default FS); x1fs FIFO usage used to intermittently crash the shell via the fork/COW-adjacent bug below, now fixed — see that entry.
[RESOLVED] No symlink support in the VFS — added `symlink`/`readlink` ops to vfs_fs_t plus a new symlink-following loop layered over the existing `resolve_at()` path-resolution choke-point in syscall.c (bounded, -ELOOP on cycles), since the VFS has no per-component vnode walk of its own — every filesystem driver does its own whole-path lookup, so the loop re-`lstat`s successive path prefixes and splices in symlink targets before handing the fully-resolved path down. New syscalls symlink/symlinkat/readlink/readlinkat (kernel + mlibc krnl sysdep), `stat()`/`lstat()` now correctly differ (the kernel was silently ignoring `AT_SYMLINK_NOFOLLOW` before), and `O_NOFOLLOW` is honored on open(). Implemented in both ext2 (real on-disk fast/slow symlinks using the existing i_block fast-symlink convention — also fixed a latent free_all_blocks() bug that would have corrupted the free-block bitmap on deleting a fast symlink) and x1fs's RAM-backed write overlay (x1fs's static/baked ramdisk image still has no symlink representation — out of scope, since create-ramdisk.py follows symlinks when packing). Confirmed end-to-end on a fresh headless boot: the real pre-existing `/usr/bin/awk -> gawk` symlink now correctly reports as a symlink via `stat`/`lstat` and `execve`s through to the real gawk binary; fresh `ln -s`/`readlink`/`cat` round-trips (absolute and relative targets) work on both ext2 and x1fs; `rm` on a symlink removes the link, not its target; a deliberate symlink cycle correctly fails with ELOOP instead of hanging.
[PARTIALLY RESOLVED] mount()/umount() syscalls now exist (real `SYS_MOUNT`/`SYS_UMOUNT`, mlibc `mount()`/`umount()`/`umount2()` all work end-to-end) and support mounting a `tmpfs` at any existing directory at runtime, backed by a fresh, deviceless x1fs instance (reuses x1fs's existing RAM-overlay code wholesale, since it's already a complete filesystem on its own — only its now-dead static-image code paths go unused for a tmpfs instance). Root-only; refuses to unmount `/` or a non-mount-point path. Real block-device mounting (a real `source` like `/dev/sdb1`) is NOT supported — this kernel has no `/dev` block-device-node infrastructure yet to name an arbitrary disk from userspace; that's its own separate follow-up. This is enough to unblock tmpfs/devtmpfs-shaped uses and is a real prerequisite step toward procfs, but "mount a second disk" and "`/etc/fstab`" specifically still aren't achievable.
No procfs/sysfs — create-ext2.sh pre-creates empty /proc and /sys directories but no filesystem backs them. ps, top, df, mount, and countless scripts that read /proc will fail or need to be avoided entirely.
mmap(MAP_SHARED) and PROT_NONE guard pages are unimplemented (syscall.c syscall_mmap returns -ENOSYS) — blocks shared-memory IPC and anything relying on shared mappings (some dynamic linker/loader patterns, shared caches, many daemons).
No networking whatsoever — no NIC driver, no socket syscalls (mlibc's socket family falls through to ENOSYS stubs), no loopback. Even a "minimal" distro is expected to at least support loopback/localhost for many tools; anything net-facing (ping, curl, ssh) is a non-starter.
No multi-user support — sysroot/etc is essentially empty (no /etc/passwd, /etc/group, /etc/shadow), no login/getty. This is a root-only, auto-exec-to-shell system, fine for a hobby OS but not a "distro" in the normal sense.
Tier 3 — Would matter for a more complete/robust system, but not blocking basic use
AHCI driver limitations — forced to polling mode due to an unresolved MSI/kernel-context register-drift bug (ahci.c), single command slot (no NCQ). Works, but no interrupt-driven I/O and no command queuing hurts performance/scalability.
SMP is detected but unused — cpu.c/apic.c park every non-boot core in a hlt loop. The scheduler (scheduler.c) is single-core only. Fine for correctness, bad for anything CPU-bound.
kmalloc is page-granular only — no slab/small-object allocator (allocator.c); every kernel allocation rounds up to whole pages. Wastes memory but isn't a functional blocker yet.
No ptrace — no gdb/strace support for userspace debugging (kernel-side debugging via debug-qemu.sh+GDB works, but that's kernel-only).
clock_settime stubbed, no RTC persistence path exposed — minor, mostly affects date-setting correctness across reboots.
[RESOLVED] `ls -l` (and anything else that formats a timestamp via localtime) used to panic mlibc with "Error opening file_window to /etc/localtime" since no tzfile was ever shipped. Fixed by adding a minimal 54-byte valid UTC TZif file at a new `env/skel/etc/localtime` (a version-controlled overlay directory merged into `sysroot/` by `test.sh`, since `sysroot/` itself is gitignored/regenerated). Confirmed via headless boot: `ls -l`, `stat`, and `date` all work correctly.
[RESOLVED] x1fs (the ramdisk format) had no write support — added a RAM-backed overlay (create/write/mkdir/unlink/rename/rmdir all work now; changes are lost on reboot, matching ramdisk semantics). ext2 remains the persistent option and is now the default (`test.sh --build`/`--debug` default to `FS=ext2`; set `FS=x1fs` explicitly to get the ramdisk instead).
Suggested next-priority order if the goal is "boots to a genuinely usable shell"
[DONE] /dev nodes (null/zero/urandom) → [DONE] TTY canonical mode + job control (Ctrl‑C/Ctrl‑Z, process groups) → [DONE] grep/sed/awk/findutils in the bootstrap manifest → [DONE] real select/poll (fd readiness, not just timeouts) → [DONE] symlinks in ext2/VFS → [DONE] permission enforcement (uid/gid checks + real chmod/chown) → [DONE] process reaping/real init (fork/wait loop, orphan reaping) → [DONE] `tcflow()` + the `xargs`+pipe hang → [DONE] FIFOs (Tier 2) → [PARTIAL] `mount()`/`umount()` + tmpfs (Tier 2) → remaining Tier-1 items are `less`/an editor (blocked on a termcap/curses port) and wiring the PS/2+framebuffer path into the TTY for non-serial use. Networking and procfs are bigger lifts and matter more for "general purpose" than for "minimally usable." Smaller worthwhile follow-ups surfaced along the way: consider porting a minimal termcap/curses library to unlock `less`, root-cause the dormant bash `sigchld_handler` bug noted in the TTY entry above (only reachable once something actually delivers a real SIGCHLD signal to a shell, which nothing did until this pass, and was reverted specifically because of this bug). [RESOLVED] The "fork/COW" bug first seen in the tcflow work and hit again by FIFOs (a child that blocks in a kernel-context wait across a multi-second window while its parent keeps running could come back with corrupted global state) was root-caused: it was never a COW/VMM bug — `duplicate_thread()` (process.c) never propagated a forked child's `fs_base` into its `kcontext`, so any forked-but-not-yet-`execve`'d process that blocked in a kernel-context wait and later woke resumed with FS_BASE=0 (a NULL TLS base) instead of corrupted memory. Fixed with a one-line propagation, mirroring the existing (correct) handling for the thread's normal `->context`. A real TCOOFF-blocking `tcflow()` implementation could likely be revisited now. [RESOLVED] The x1fs-only data-loss quirk found while re-verifying the fs_base fix (a backgrounded FIFO reader whose output is redirected to a file lost the data on x1fs specifically) turned out to be x1fs always reporting `st_ino == 0` for every entry, false-positiving GNU cat's "don't copy a file onto itself" safety check for any (fifo, regular-file) pair. Fixed by giving x1fs real per-entry inode numbers (static entries numbered by string-table index, dynamic entries by a per-instance counter). [RESOLVED] `vmarea_try_cow()` (mmap.c)'s physical-page bookkeeping leak (never removed the old allocation record it unmapped, leaking one physical page per fork+COW-write pair) is fixed — the fix required care: an initial attempt freed the old pages before allocating the new ones, letting the allocator hand back the same physical frames and get zeroed before the copy ran, corrupting the VMA's contents instead of just leaking memory. Caught via an isolation test before shipping; corrected by removing the bookkeeping record early but deferring the actual physical free until after the copy completes. See mount()/umount() entry above for that Tier-2 item, now partially resolved (tmpfs works; a real disk source still doesn't). [RESOLVED] The intermittent crash right at prompt startup, previously assumed to be a pre-existing bash/mlibc bug, turned out to be three real kernel bugs: a missing x86-64 red zone reservation in signal delivery, signals with custom handlers never being dequeued when they interrupt a kernel-context sleep (causing an infinite spurious-EINTR retry loop — visible as the prompt reprinting instantly, over and over), and a real ABI mismatch in `pselect()` (its `num_events` out-parameter was never populated, leaving callers with garbage ready-counts). All three fixed; a real interactive command round-trip now succeeds. One new, so-far-unexplained crash surfaced afterward in bash's own `copy_word_list` (poison-pattern `CR2`, looks like a use-after-free) — not yet root-caused, worth a dedicated follow-up.
