KRNL vs. a minimal usable Linux distro — gap analysis
Based on a full read of kernel/src, the mlibc syscall shim, and the userspace bootstrap manifest. Current state in one line: boots via UEFI/Limine → mounts ext2 (AHCI) or a ramdisk → execs init → execs bash with full GNU coreutils, over a serial console. That's a real foundation — closer to "minimal distro" than most hobby kernels get. The gaps below are sorted by how much they block generic, everyday usability (not by implementation difficulty).

Tier 1 — Blocks basic interactive/day-to-day use
[RESOLVED] TTY line discipline (canonical mode, echo, Ctrl‑C/Ctrl‑Z signal generation) — tty.c now implements real canonical-mode line buffering/editing (VERASE/VKILL/VEOF), ECHO with OPOST/ONLCR, and ISIG-driven SIGINT/SIGQUIT/SIGTSTP delivered to the foreground process group. Real process groups exist (process_t.pgid/sid, setpgid/getpgid/setsid/getsid syscalls, mlibc's stubs replaced), SIGCHLD is delivered on child exit/stop/continue, and a kernel-wide bug where signals were never delivered to threads blocked in a kernel-context wait (waitpid/nanosleep/tty read/pipe/futex) was found and fixed. Ctrl‑C/Ctrl‑Z/fg/bg/jobs all confirmed working against `cat`. Known residual gaps: bash's own readline occasionally crashes on signal delivery (pre-existing bug in bundled bash/mlibc, out of scope — see memory), and `fg` resuming a stopped job doesn't always cleanly restore interactive input.
[RESOLVED] No /dev device-node infrastructure — /dev/null, /dev/zero, /dev/random, /dev/urandom now exist (memdev.c) alongside /dev/tty0.
No text-processing toolset — sys-apps.yml only builds bash + coreutils 8.32. There's no grep, sed, awk, findutils, less/more, or a text editor (vi/nano). Coreutils alone (ls/cp/mv/cat/...) isn't enough to call a system "usable" for real work.
[PARTIALLY RESOLVED, see above] — grep/sed/gawk/findutils added to sys-apps.yml and confirmed working (including `find`'s real directory traversal, which needed new fchdir/openat/fstatat(fd_path) kernel support — see below). `less`/`more`/an editor are still missing (less needs a termcap/curses library that isn't cross-compiled for this target — a separate, larger porting effort). `xargs` has a known bug: invoking a child command produces "I/O error (EIO)" on the child's own I/O, and piping `find | xargs <cmd>` specifically can hang the shell (not yet root-caused — narrower than the general findutils fix, likely related to how xargs redirects the child's stdin).
Keyboard/console not wired for local (non-serial) use — the PS/2 driver (ps2/keyboard.c) and framebuffer text renderer (framebuffer.c) both work standalone but are never connected to the TTY/stdin path; only a serial line is usable as a terminal today.
Permissions are entirely unenforced — vfs.c has zero uid/gid/mode checks (confirmed by grep — no EACCES, no mode-bit tests anywhere). chmod/chown aren't even real syscalls (fchownat is a hard -ENOSYS stub, syscall.c). Any file is readable/writable/executable by anyone; there's effectively no security boundary between processes.
No process reaping / real init — init.c is 33 lines: print banner, execv("/usr/bin/bash"), done. No fork/wait loop, no orphan reaping, no /etc/inittab, no /etc/fstab mounting, no respawn. Orphaned/zombie processes will accumulate forever; there's no supervision if bash ever exits or crashes.
Tier 2 — Missing core OS functionality expected by generic userspace software
[RESOLVED] select/poll are fake (fd readiness always reports ready) — pselect now does real fd-readiness checking instead of reporting every requested fd ready unconditionally. Added a `poll` op to vfs_fs_t (device_major/minor/path/for_write -> ready?), NULL meaning "always ready" (correct for regular files/memdev, whose I/O is synchronous and never blocks); tty.c implements it against the same cooked-buffer/EOF state tty_read already blocks on, and pipes are checked directly against their buffer count/reader/writer state (mirroring pipe_read/pipe_write's own blocking conditions). There's still no true event-driven multi-fd wait (sleep()/wakeup() only support one wait channel per call), so an unready set is polled at the scheduler's HPET tick granularity (~77ms) until something is ready or the timeout elapses — correct, if not maximally efficient; still the right fix for correctness-sensitive callers (anything that only reads/writes an fd after select/pselect reports it ready). Confirmed via a fresh kernel build + full headless serial-console boot to a bash prompt with no regressions in the boot path.
No named pipes / FIFOs at the kernel level — coreutils ships mkfifo/mknod, but pipes (pipe.c) are anonymous-only with no VFS-visible FIFO node type. Running mkfifo produces a file that can't actually function as a FIFO.
No symlink support in the VFS — no filesystem in vfs.c implements symlinks. Breaks common FHS conventions (/bin → usr/bin, /lib64 symlinks, etc.) and any software that relies on them.
No mount/umount syscalls — filesystem layout is fixed at boot (root + one hard-coded tty mount). Can't mount a second disk, tmpfs, procfs, or devtmpfs at runtime.
No procfs/sysfs — create-ext2.sh pre-creates empty /proc and /sys directories but no filesystem backs them. ps, top, df, mount, and countless scripts that read /proc will fail or need to be avoided entirely.
mmap(MAP_SHARED) and PROT_NONE guard pages are unimplemented (syscall.c syscall_mmap returns -ENOSYS) — blocks shared-memory IPC and anything relying on shared mappings (some dynamic linker/loader patterns, shared caches, many daemons).
No networking whatsoever — no NIC driver, no socket syscalls (mlibc's socket family falls through to ENOSYS stubs), no loopback. Even a "minimal" distro is expected to at least support loopback/localhost for many tools; anything net-facing (ping, curl, ssh) is a non-starter.
No multi-user support — sysroot/etc is essentially empty (no /etc/passwd, /etc/group, /etc/shadow), no login/getty. This is a root-only, auto-exec-to-shell system, fine for a hobby OS but not a "distro" in the normal sense.
Tier 3 — Would matter for a more complete/robust system, but not blocking basic use
AHCI driver limitations — forced to polling mode due to an unresolved MSI/kernel-context register-drift bug (ahci.c), single command slot (no NCQ). Works, but no interrupt-driven I/O and no command queuing hurts performance/scalability.
SMP is detected but unused — cpu.c/apic.c park every non-boot core in a hlt loop. The scheduler (scheduler.c) is single-core only. Fine for correctness, bad for anything CPU-bound.
kmalloc is page-granular only — no slab/small-object allocator (allocator.c); every kernel allocation rounds up to whole pages. Wastes memory but isn't a functional blocker yet.
No ptrace — no gdb/strace support for userspace debugging (kernel-side debugging via debug-qemu.sh+GDB works, but that's kernel-only).
clock_settime stubbed, no RTC persistence path exposed — minor, mostly affects date-setting correctness across reboots.
x1fs (the ramdisk format) has no write support (no create/unlink/mkdir/rename) — fine since ext2 is the full-featured option, but the ramdisk boot path is read-mostly.
Suggested next-priority order if the goal is "boots to a genuinely usable shell"
[DONE] /dev nodes (null/zero/urandom) → [DONE] TTY canonical mode + job control (Ctrl‑C/Ctrl‑Z, process groups) → [DONE] grep/sed/awk/findutils in the bootstrap manifest → [DONE] real select/poll (fd readiness, not just timeouts) → symlinks in ext2/VFS → permission enforcement (uid/gid checks + real chmod/chown). Networking and procfs are bigger lifts and matter more for "general purpose" than for "minimally usable." Smaller worthwhile follow-ups surfaced along the way: fix the `xargs`+pipe hang, implement `tcflow()`, consider porting a minimal termcap/curses library to unlock `less`. [RESOLVED] The intermittent crash right at prompt startup, previously assumed to be a pre-existing bash/mlibc bug, turned out to be three real kernel bugs: a missing x86-64 red zone reservation in signal delivery, signals with custom handlers never being dequeued when they interrupt a kernel-context sleep (causing an infinite spurious-EINTR retry loop — visible as the prompt reprinting instantly, over and over), and a real ABI mismatch in `pselect()` (its `num_events` out-parameter was never populated, leaving callers with garbage ready-counts). All three fixed; a real interactive command round-trip now succeeds. One new, so-far-unexplained crash surfaced afterward in bash's own `copy_word_list` (poison-pattern `CR2`, looks like a use-after-free) — not yet root-caused, worth a dedicated follow-up.
